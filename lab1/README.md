# task_planner — Планувальник завдань

Лабораторна робота 1 з дисципліни «Програмування мовою Dart».
Тема: функції, замикання, колекції, рядки, дати. Варіант 10 — «Планувальник завдань»
(завдання: назва, проєкт, пріоритет, термін виконання, статус, оцінка трудомісткості).

Консольна програма розбирає набір CSV-подібних рядків, відкидає пошкоджені,
перевіряє діапазони значень і будує агреговані показники та текстовий звіт.
**Класи в цій роботі не використовуються** — тільки записи (records), колекції та функції.

## Запуск

```bash
dart pub get
dart run                      # звіт на поточну дату
dart run bin/task_planner.dart 2026-10-15   # звіт на задану дату (відтворюваний вивід)
dart analyze
dart test
```

> Примітка. Якщо шлях до проєкту містить кириличні символи, `dart test` у Dart 3.13
> завершується повідомленням `package_config.json did not contain its own root package`
> (проблема інструменту з кодуванням шляху). У каталозі з латинським шляхом усі тести
> проходять.

## Формат вхідних даних

```
id;назва;проєкт;пріоритет;створено;термін;статус;години
WEB-101;Верстка головної сторінки;WEB;3;2026-09-01;2026-10-10;done;12
```

До полів варіанта додано два поля: `id` (потрібен для перевірки регулярним виразом
і маскування) та дату створення (потрібна для обчислення віку запису в днях).

Набір містить 18 рядків: 12 коректних, 4 пошкоджені (відсутнє поле, нечисловий
пріоритет, неіснуюча дата `2026-09-31`, нечислова трудомісткість) і 2, що
розбираються, але не проходять перевірку діапазонів.

## Структура програми

| Файл | Призначення |
|---|---|
| `bin/task_planner.dart` | Точка входу: лише послідовність кроків і друк результатів |
| `lib/task_planner.dart` | Бібліотека-фасад, реекспортує модулі |
| `lib/constants.dart` | Усі межі, статуси, роздільники — замість «магічних» значень |
| `lib/model.dart` | Псевдоніми типів `Task`, `ParseResult`, `TaskComparator`, `TaskPredicate`, `EstimateStats` |
| `lib/data.dart` | Константний список вхідних рядків |
| `lib/parsing.dart` | `parseLine` — розбір рядка без винятків |
| `lib/validation.dart` | `validateTask` — перелік порушень діапазонів і узгодженості |
| `lib/pipelines.dart` | Конвеєри фільтрації, перетворення, згортання, групування, сортування |
| `lib/closures.dart` | Лічильник-замикання і фабрики предикатів |
| `lib/text_utils.dart` | Регулярні вирази з іменованими групами, маскування, форматування |
| `lib/dates.dart` | Строгий розбір дат і арифметика дат через `difference`/`Duration` |
| `lib/report.dart` | `buildReport` з іменованими параметрами та `StringBuffer` |
| `test/` | Модульні тести основних функцій |

**Чому так.** Логіка винесена в `lib/`, щоб у ЛР2 її можна було переписати на класи
й порівняти, а в ЛР3 — покрити тестами без зміни точки входу. `bin/` не містить
обчислень, лише виклики й друк. Кожен файл відповідає одній відповідальності
(розбір, перевірка, обробка, вивід), тому модулі залежать один від одного в один бік:
`constants/model → text_utils/dates → parsing/validation → pipelines → report → bin`.
Підкаталог `lib/src/` не вводився: за методичкою канонічна структура пакета — з ЛР4.

**Альтернативи, які розглядалися:** один файл `main.dart` (простіше, але змішує
розбір, обробку й вивід і погано тестується); поділ лише на `bin/` + один `lib/`-файл
(виходить понад 600 рядків у файлі).

## Вибір типів даних

- **Іменований запис `Task`** замість `Map<String, Object>`: поля типізовані, компілятор
  перевіряє звернення до них, записи порівнюються за значенням. Класи заборонені умовою
  роботи, а `Map` втратив би статичну типізацію і потребував би приведень типів.
- **`ParseResult = ({Task? task, String? error})`** — результат розбору разом із причиною
  відмови. Порівняно з поверненням просто `Task?` дозволяє показати користувачу, *чому*
  рядок відхилено. Винятки (`try/catch`) не використовуються: пошкоджений рядок —
  очікувана ситуація, тому застосовано `int.tryParse`, `double.tryParse`, `DateTime.tryParse`.
- **`double` для годин** — оцінки бувають дробовими (8.5 год).
- **`String` для статусу + `Set<String> allowedStatuses`** — перелічення (`enum`) з членами
  за методичкою вводиться в ЛР2; `Set` дає перевірку належності за O(1).
- **`Map<String, List<Task>>`** для групування за проєктом, `Map<String, double>` — для сум.
- **Дати в UTC.** `DateTime.tryParse('2026-09-31')` не повертає `null`, а нормалізує дату
  до 1 жовтня, тому компоненти додатково звіряються з групами регулярного виразу.
  Дати переводяться в UTC, бо в місцевому часі `difference` через перехід на зимовий
  час (25.10.2026) дає 23 або 25 годин і `inDays` може помилитися на день.
- **Typedef для функціональних типів** (`TaskComparator`, `TaskPredicate`) — роблять
  сигнатури `sortTasks` і фабрик предикатів читабельними.

## Залежності

| Пакет | Тип | Навіщо | Альтернатива |
|---|---|---|---|
| `lints` | dev | Набір правил `recommended` для `dart analyze` (вимога методички) | `very_good_analysis` — суворіший, але сторонній; обрано офіційний пакет команди Dart і додано кілька правил вручну |
| `test` | dev | Модульні тести функцій розбору, перевірки та конвеєрів | Ручні перевірки через `assert` у `main` — не дають звіту й не запускаються окремо |

Залежність `path`, яку додає шаблон `dart create`, вилучено — вона не використовується.
Пакет `collection` не підключався: `firstOrNull` і `nonNulls` є в `dart:core` з Dart 3.0,
а групування реалізовано через `fold`.

## Оператор `!`, `late`, `dynamic`

У коді **не використовуються**. Значення nullable-типів обробляються через `?.`, `??`,
перевірку на `null` з просуванням типу та зіставлення зі зразком
(`if (result case (task: null, :final String error))`). Для `namedGroup`, що повертає
`String?`, використано `?? ''` разом з `int.tryParse`.

## Налаштування аналізатора

`analysis_options.yaml` підключає `package:lints/recommended.yaml` і вмикає
`strict-casts`, `strict-inference`, `strict-raw-types`, а також правила
`public_member_api_docs`, `prefer_final_locals`, `prefer_single_quotes`,
`directives_ordering` та інші.
