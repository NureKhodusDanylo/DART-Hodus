# task_planner — Планувальник завдань (ЛР3)

Лабораторна робота 3 з дисципліни «Програмування мовою Dart».
Тема: асинхронність — `Future`, `Stream`, ізоляти. Варіант 10 — «Планувальник завдань».

Модель з ЛР2 доповнено асинхронним сховищем, джерелом подій на `StreamController`
і винесенням важкого обчислення в ізолят. Джерело даних імітується затримками
`Future.delayed`; справжні файли й мережа з'являться в ЛР4. Попередні етапи —
папки `lab1/` і `lab2/` (теги `lab1`, `lab2`).

## Запуск

```bash
dart pub get
dart run          # демонстрація: 11 розділів, приблизно 10 секунд
dart analyze
dart test         # 22 тести, з них 11 — на асинхронний код
```

> Якщо шлях до проєкту містить кириличні символи, `dart test` у Dart 3.13 завершується
> повідомленням `package_config.json did not contain its own root package`. У каталозі
> з латинським шляхом усі тести проходять.

## Що додано

| Файл | Призначення |
|---|---|
| `lib/async_repository.dart` | `AsyncRepository<T extends Identifiable>`: `load`, `loadOrThrow`, `loadAll`, `save`, `saveAll`, `delete` повертають `Future`; `watchAll` — генератор `async*` |
| `lib/task_events.dart` | Запечатана ієрархія подій `TaskEvent` і джерело `TaskEventSource` на `StreamController` (одноразове або широкомовне) |
| `lib/workload.dart` | `simulateWorkload` — важке синхронне обчислення для `Isolate.run`; глобальна змінна `simulationRuns` |
| `lib/timing.dart` | `measure` (вимірювання через `Stopwatch`) і `slowOperation` (операція 500 мс, можливо з помилкою) |
| `test/async_test.dart` | Тести сховища, потоків, `.wait` та ізолята з `group`, `setUp`, `tearDown`, `expectLater` |

## Рішення

- **Розподіл коду.** Усі нові засоби — у `lib/` (сховище, події, моделювання,
  вимірювання часу) і покриті тестами; `bin/task_planner.dart` лише послідовно демонструє
  пункти завдання й друкує виміри.
- **Затримка сховища — параметр конструктора.** У демонстрації — 300 мс, у тестах —
  `Duration.zero`, тож тести виконуються миттєво й не залежать від таймінгів.
- **`watchAll` — генератор `async*`, а події — `StreamController`.** Генератор лінивий і
  сам завершується, коли закінчуються елементи; контролер потрібен там, де події
  надходять ззовні (`emit`), і його треба закрити явно, інакше він тримає ресурси.
- **Кожна підписка має точку скасування.** Результат `listen()` зберігається у змінну
  `StreamSubscription` і скасовується через `await sub.cancel()`.
- **Лінти `unawaited_futures` і `discarded_futures` увімкнено.** Під час першого запуску
  вони підсвітили 5 місць: два `source.close()` без `await` (справжні недоліки — додано
  `await` або `unawaited` там, де закриття завершиться лише після читання потоку),
  `repo.save(draft)` і виклик у `try` без `await` (навмисні демонстрації «забутого await»,
  позначені `unawaited(...)`) та `Future` у рядковій інтерполяції (замінено на
  `toString()`).
- **Ізолят лише для важкого синхронного обчислення.** `simulateWorkload` генерує й
  сортує 3 000 000 значень; у головному ізоляті вона блокує цикл подій, в
  `Isolate.run` — ні (видно за кількістю спрацювань таймера).

**Альтернативи, які розглядалися:** `StreamController` замість генератора `async*` для
`watchAll` (довелося б вручну закривати контролер); `Isolate.spawn` із `SendPort`/`ReceivePort` замість
`Isolate.run` (більше коду для одноразового обчислення без обміну повідомленнями); `fake_async` для тестів (не
знадобився — затримка сховища обнуляється параметром).

## Залежності

| Пакет | Тип | Навіщо | Альтернатива |
|---|---|---|---|
| `lints` | dev | Правила `recommended` для `dart analyze` | `very_good_analysis` — сторонній |
| `test` | dev | Обов'язкові з ЛР3 модульні тести; матчери `emitsInOrder`, `emitsError`, `completion`, `throwsA` для асинхронного коду | `fake_async` для керування часом — не знадобився, бо затримку сховища можна обнулити |

`dart:async` і `dart:isolate` — частина SDK, окремих пакетів не потрібно.

## Оператор `!`, `late`, `dynamic`

- **`late`** — лише в тестах, два оголошення в `test/async_test.dart`:
  `late AsyncRepository<Task> repo` і `late TaskEventSource source`. Змінні ініціалізуються в `setUp` перед кожним тестом,
  тому оголосити їх ініціалізованими в місці оголошення неможливо, а nullable-тип
  змусив би писати перевірки в кожному тесті. Це стандартний патерн `package:test`.
- **`!` і `dynamic`** не використовуються.
