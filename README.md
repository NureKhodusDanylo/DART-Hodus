# task_planner — Планувальник завдань (ЛР2)

Лабораторна робота 2 з дисципліни «Програмування мовою Dart».
Тема: класи, ієрархії, домішки, узагальнення, записи. Варіант 10 — «Планувальник завдань».

Програму з ЛР1 (функції над записами) переписано в об'єктно-орієнтовану модель:
незмінний клас-сутність `Task`, запечатана ієрархія станів, перелічення пріоритетів,
домішка для сутностей з терміном, методи розширення та узагальнене сховище.
Стан коду ЛР1 збережено в історії під тегом `lab1`.

## Запуск

```bash
dart pub get
dart run bin/task_planner.dart 2026-10-15   # демонстрація на задану дату
dart analyze
dart test
```

> Якщо шлях до проєкту містить кириличні символи, `dart test` у Dart 3.13 завершується
> повідомленням `package_config.json did not contain its own root package`. У каталозі
> з латинським шляхом усі тести проходять.

## Модель предметної області

| Тип | Вид | Призначення |
|---|---|---|
| `Identifiable` | `interface class` | Контракт «має `id`» для узагальненого сховища |
| `Entity` | абстрактний клас | Спільна база сутностей: `id`, `displayName`, `toString` |
| `Task` | `final class` | Незмінне завдання: `const`-конструктор, `fromCsv`, фабричний `cached`, `==`/`hashCode` |
| `Project` | `final class` | Проєкт без терміну, класичний `const`-конструктор |
| `Milestone` | `final class` | Віха з терміном, оголошена первинним конструктором (Dart 3.13) |
| `Scheduled` | `mixin … on Entity` | Термін, дні до терміну, прострочення — для `Task` і `Milestone` |
| `TaskStatus` | `sealed class` | Стан: `Todo`, `InProgress`, `Done`, `Blocked` |
| `Priority` | `enum` з полями | Пріоритет 1–5 з назвою й ознакою «високий» |
| `Repository<T extends Identifiable>` | узагальнений клас | Сховище з пошуком за `id` |
| `CalendarDate`, `StrictDateParsing`, `TaskCollection` | розширення | Методи для `DateTime`, `String`, `Iterable<Task>` |
| `Progress` | запис | Кілька значень з `progressOf` |

## Чому саме така структура

- **`Entity` — абстрактний клас, а `Identifiable` — інтерфейс.** Сховищу потрібен лише
  контракт `id`, тому обмеження типу — інтерфейс; спільна реалізація (поле `id`,
  `toString`) — в абстрактному класі.
- **Стан — `sealed class`, а не `enum`.** Підтипи мають власну поведінку (`progress`,
  `isFinished`), а `switch` без `default` перевіряється компілятором на вичерпність:
  додавання нового стану вказує на всі місця, де його не враховано.
- **Пріоритет — `enum` з членами.** Набір значень закритий і не має власних даних,
  крім рівня й назви. Рівень 9 тепер неможливо представити, тому ця перевірка
  перейшла з валідатора в розбір.
- **Домішка `Scheduled`, а не надклас.** Термін мають завдання й віхи, але не проєкти.
  Винесення терміну в `Entity` дало б проєкту безглуздий термін, а окремий надклас для
  `Task` і `Milestone` заборонив би їм інше успадкування. Обмеження `on Entity` дає
  домішці доступ до `id` і `displayName`.
- **`Task.fromCsv` + `Task.tryParse`.** Конструктор не може повернути `null`, тому
  `fromCsv` кидає `FormatException` (для довірених даних), а `tryParse` повертає запис
  «завдання або причина» для даних, які можуть бути пошкоджені. Блоків `try/catch`
  у коді немає.
- **Фабричний `Task.cached`.** Повертає вже створений екземпляр для того самого рядка —
  такого не вміє генеративний конструктор.

## Оператор `!`, `late`, `dynamic`

У коді **не використовуються**. Nullable-значення обробляються через `?.`, `??`,
просування типу та зіставлення зі зразком (`if (... case final Task task)`). У
`Task._parseOrThrow` замість `!` використано `task ?? (throw FormatException(...))`.
